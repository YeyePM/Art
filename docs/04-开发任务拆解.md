## 0. 怎么读这份文档

这份文档只解决一件事：**把 MVP 拆成前端和后端各自能立刻动手的任务，并规定顺序。**

两条硬约定：

1. **先定接口契约，再动手**（第 2 节）。契约不定，前端只能干等后端。
2. **顺序是"垂直切片"，不是"先做完后端再做前端"**。每个里程碑都交付一个"能看见的完整功能"。理由：水平分层会让你两周后才第一次看到界面，所有风险堆到最后一次性爆发。

每个任务都写清三件事：**做什么 / 产出物 / 怎么算完成**。

## 2. 接口契约（最重要的一节）

> 契约定完，前端就能对着假数据独立开工，不必等后端。

| # | 方法 | 路径 | 请求 | 响应 | 里程碑 |
| --- | --- | --- | --- | --- | --- |
| 1 | GET | `/api/health` | — | `{ok: true}` | M0 |
| 2 | GET | `/api/today` | — | `{date, questions[], progress:{done,total}, checked_in}` | M1 / M2 / M4 |
| 3 | POST | `/api/answers` | `{question_id, user_answer, self_grade?}` | `{correct, explanation, reference_answer, ai_comment, ai_errors, next_review_at}` | M2 / M3 |
| 4 | GET | `/api/stats` | — | `{current_streak, longest_streak, total_days, accuracy:{overall, by_type}}` | M4 |
| 5 | GET | `/api/weekly` | — | `{batch_id, starts_on, artwork, excerpt, open_question}` | M5 |
| 6 | POST | `/api/artworks/note` | `{artwork_id, content}` | `{ok: true}` | M5 |
| 7 | POST | `/api/open-questions/answer` | `{open_question_id, content}` | `{ok: true}` | M5 |
| 8 | POST | `/api/flag` | `{target_type, target_id, note?}` | `{ok: true}` | M6 |
| 9 | GET | `/api/images/{filename}` | — | 图片二进制 | M5 |
| 10 | GET | `/api/home` | — | `{date, today_progress:{done,total}, stats:{current_streak, accuracy}, weekly_summary}` | M7 |
| 11 | GET | `/api/stats` 扩展 | — | 同上接口增加 `calendar[]`（打卡日历，只标完成 / 未完成） | M7 |
| 12 | POST | `/api/fragments` | multipart：`file`、`kind`（artwork/text）、`note?` | `{id, status:"pending"}` | M9 |
| 13 | GET | `/api/fragments` | `?q=`（可选） | `fragments[]` | M9 |
| 14 | POST | `/api/push/test` | `{at?}` | `{ok: true, sent, reason, date, body?}` | M8 |

### `questions[]` 单项结构约定

```json
{
  "id": "q_001",
  "type": "objective",
  "stem": "题干文字",
  "options": ["A 选项", "B 选项", "C 选项", "D 选项"],
  "image_url": "/api/images/xxx.jpg",
  "is_review": false,
  "tags": ["宋", "文人画"]
}
```

`type` 取四个值之一：`objective`（客观题）/ `term`（名词解释）/ `image`（图像辨识）/ `essay`（开放论述）。

### 一条必须守住的规则

**`/api/today` 绝不返回答案和解析。** 答案与解析只在 `POST /api/answers` 的响应里返回——包括主观题的参考答案，也必须等提交后才给。否则前端能提前拿到答案，自评环节就失效了。

### 前端 mock 约定

前端在后端就绪前，用一份 `mock/today.json` 按上面的结构造 10 道题（四种题型都要有、至少 1 道 `is_review: true`），这样 UI 可以先跑通。

### 等待方式（2026-10-08 定）

`/api/today` 走**同步阻塞**：后端把 10 题凑齐（含调 AI 补题）才响应，前端全程显示 loading，**不加 `generating` 字段、不做轮询**。当天二次打开因已落库，是秒开。

| 里程碑 | 交付什么（打开浏览器能看见的） |

| **M5 每周一批** | 能看到画、写一句能存、能读摘录和开放问题 |

| **M7 主界面** | 打开先看到横排概览卡（今日的题 / 学习进度 / 本周一批），鼠标左右移动驱动整排平移，回车落到今日页；进度页可看 |

**M1 之后的每一步都是可用的**——即使中途停下，也已经有东西能用。

## 4. 后端任务清单

### T1 · 骨架与数据层（M0）

- **做什么**：按 **npm workspaces 建单仓两包**（`app/web/` 前端 + `app/api/` 后端，一条 `npm run dev` 同时起）；起 Node 服务；用 **`better-sqlite3` 手写 SQL** 连通 SQLite；建全部表（见 [02-技术方案.md](./02-技术方案.md) 第五节，**其中 `fragments` 表虽属 v0.2 也一并建好**，避免以后改数据结构）；实现 `/api/health`。
- **产出物**：能启动的服务 + 一个含全部表的数据库文件。
- **怎么算完成**：访问 `/api/health` 返回 `{ok:true}`；用数据库工具能看到 02 第五节列出的全部表。

### T2 · 标签体系与组题规则（M1）

- **做什么**：定义标签常量（中外 / 时期 / 流派 / 作者 / 作品 / 技法）；实现组题规则——题型上限（论述 ≤1、名词 ≤2、图像辨识 ≤2）、中外混合、不按时间线排序；算出"当前有几题、还缺几题"。
- **产出物**：一个能产出（或补齐）10 题的组题函数。
- **怎么算完成**：手工塞 30 道假题进库，能稳定产出 10 题，且题型数量符合上限。

### T3 · AI 生成与落库（M1）— **关键路径**

- **做什么**：拼提示词（含标签要求、**难度定位**、题型上限、JSON 输出格式）；调 AI、解析 JSON、算内容指纹去重、写入 `questions`；**把思考压到最低档**（省钱，见技术方案第七节）。
- **难度定位**：题库对标各大美院美术史考研真题（见 [03-MVP-Spec.md](./03-MVP-Spec.md) 第 2 节"难度定位"）。提示词里必须写死这一条，否则 AI 默认出通识题（如"南北宗论"），对目标用户太浅。
- **产出物**：一个"缺几题就补几题"的生成函数。
- **怎么算完成**：缺 10 题时能生成并入库 10 道；重复调用不会产生重复题；同一天内不会二次调用 AI。

#### T3 生成提示词（**2026-10-08 定稿，直接用**）

系统提示词，原样发给 `glm-5.3-flash`（变量只有两个：`{N}` 缺题数、`{元数据}` 图像辨识题的博物馆元数据）：

```text
你是我的美术史复盘出题助手。我的背景：油画专业硕士在读，美术史功底远高于普通爱好者。

【任务】
生成 {N} 道题，补齐今天的每日 10 题。

【难度】
对标央美 / 国美 / 清美等院校美术史考研真题。严禁通识送分题
（如"南北宗论"、"文艺复兴三杰是谁"）。
难度档要拉开：基础 / 进阶 / 挑战 都要出现。

【配额与分布】
- 题型上限：开放论述 ≤ 1、名词解释 ≤ 2、图像辨识 ≤ 2，其余为客观题
- 中国美术史与外国美术史混合出现，不按时间线排序
- 覆盖范围：整个美术史，从史前到当代都要能出，不许集中在某一时期

【事实纪律（最重要，违反即作废）】
- 年代、作者、流派、作品名一旦不确定，宁可不写也不要编
- 有疑问直接在 explanation 里标注"存疑"，不要含糊过去
- 图像辨识题不许靠"看"去认作者和年代：作者与年代一律以随题给你的
  博物馆元数据为准，你只负责写风格依据和三个干扰项
  （元数据：{元数据}）
- 开放论述题优先取"创作实践"方向（笔触该不该被看见、完成感从哪来、
  写生与重构的关系等），要有争议点，不给标准答案

【输出】
只输出一个 JSON 对象。不要解释、不要客套话、不要用 markdown 代码块包裹：

{
  "hook": "一句不剧透的引子，20 字以内，用于当天桌面通知。严禁出现'你还没做''还差几题''连续要断了'这类催办话",
  "questions": [
    {
      "type": "objective | term | image | essay",
      "stem": "题干",
      "options": ["A ...", "B ...", "C ...", "D ..."],
      "answer": "参考答案；objective / image 给正确选项；essay 写'参考思路'",
      "explanation": "解析：这道题的考点是什么 + 最容易错在哪",
      "difficulty": "基础 | 进阶 | 挑战",
      "tags": ["宋", "文人画"]
    }
  ]
}

objective 与 image 必须给 4 个 options；term 与 essay 的 options 填 null。
```

**调用参数上必须做两件事**（不在提示词里）：

1. **把思考压到最低档**——`glm-5.3-flash` **关不掉思考**（`thinking.type=disabled` 会被 1210 拒掉），改传 `reasoning_effort: 'low'`。实测同一提示词：默认档 29842 输出 token（思考 25774）/ 266 秒，low 档 2785（思考 24）/ 71 秒，成本约 1/10。**已落地在 `src/ai/zhipuClient.js`**。
2. `response_format` 若能约束成 JSON 就用上；否则解析前先剥掉可能出现的 ```json 包裹。

### T4 · 今日会话接口（M1）

- **做什么**：实现"补足到 10 题"的组装顺序（昨日剩余 → 到期复习题 → AI 补足）；写 `daily_sessions`；实现 `GET /api/today`，**不返回答案与解析**。
- **产出物**：`/api/today` 可用。
- **怎么算完成**：首次访问生成并落库；再次访问返回**完全相同的题目**且不再调 AI；手工把进度改成 6/10 后，第二天访问先补 4 题、再发新题**补足到 10 题**（不是 14 题）。

### T5 · 判分接口（M2）

- **做什么**：实现 `POST /api/answers`——客观题 / 图像辨识题一次提交自动判分；名词解释 / 论述题**由 AI 判**（`ai/gradeAnswer.js` + `prompts/grade-answer.txt`，同步等十几秒），判完即落库并返回 `correct` + `ai_comment` + `ai_errors` + `reference_answer` + `explanation`；**用户不认可时带 `self_grade` 再提交一次即改判**（覆盖 `is_correct`、`is_self_graded=1`，AI 原始判定留在 `ai_correct`）；**AI 调不通则返回 `correct:null`+`ai_failed:true` 且不落库**，用户带 `self_grade` 提交即走改判分支落库。
  - **客观题不交给 AI**：答案是确定的选项字母，直接比零延迟零成本，AI 反而更慢还可能判飘。
  - **主观题为什么给 AI 判**：论述题提示词本来就"不给标准答案"，AI 判的是立场是否明确 / 有没有具体作品史实 / 论证是否自洽，**事实性硬错误（作者 / 年代 / 流派 / 归属 / 地域）判 false 并写进 `ai_errors`**——这正是"AI 判完我来反馈"要的入口。详见 [specs/01 一之二](../specs/01-接口契约.md)。
- **产出物**：`/api/answers` 可用。
- **怎么算完成**：四种题型都能提交并返回正确结果；答案与解析**只在此接口返回**；改判能覆盖判定且 AI 点评不丢；AI 失败时不落库、降级提示用户自己定。

### T6 · 错题队列与遗忘曲线（M3）— **逻辑最易错**

- **做什么**：答错入队（间隔 1 天、连对计数 0）；复习答对 → 计数 +1、间隔推进 1→3→7→15；复习答错 → 计数归零、间隔退回 1 天；**走完全程才出队**（在 15 天节点答对时出队，等价于连对 4 次。2026-10-08 改，原"连对 2 次"作废）；组题时把"到期"复习题插进队列。
- **产出物**：`review_queue` 的完整读写逻辑。
- **怎么算完成**：答错一题 → 改系统日期 +1 天 → 它以 `is_review:true` 出现 → 答对 → 改日期 +3 天 → 再答对 → 改日期 +7 天 → 再答对 → 改日期 +15 天 → **再答对才出队**，此后不再出现；中途任何一次答错，间隔退回 1 天重来。（**必须逐条走完四个节点**）
  - **已实现**（2026-10-08）：自测**不靠改系统日期**，而是服务层的 `applyVerdictToReviewQueue({questionId, correct, date})` 显式收 `date`，`verify-t6.js` 就是"一天走完 26 天"。接口不给前端传日期。

### T7 · 打卡与统计（M4）

- **做什么**：完成 10 题额度（含补做）后写 `checkins`；计算当前连续 / 最长连续 / 总完成天数 / 正确率；实现 `GET /api/stats`。
- **产出物**：`/api/stats` 可用。
- **怎么算完成**：做完 10 题后数字 +1；手工造一段"中间断了两天"的记录，验证**当前连续归零但最长连续与总天数保留**。
  - **已实现**（2026-10-08）：规则在 `services/stats.js`（`maybeCheckIn` / `getStats`），触发点是 `grading.js` 里"真的写下了作答"的分支。"完成 10 题"落成"做完当天题单"，自测用虚拟日期的会话 + 服务层显式传 `date` 复现，`verify-t7.js` 24/24。详见 [specs/04](../specs/04-核心规则.md) 第三节实现说明

### T8 · 每周一批生成（M5）

- **做什么**：按**滚动 7 天**判断是否需要新批次；生成 1 段书籍摘录 + 1 个开放问题 + 选定 1 张画；写 `weekly_batches` / `excerpts` / `open_questions`；实现 `GET /api/weekly`。
- **产出物**：`/api/weekly` 可用。
- **怎么算完成**：距上次批次满 7 天才生成新批次；未满时返回当前批次（内容不变）。
  - **已实现**（2026-10-08）：规则在 `services/weeklyBatch.js`（`needsNewBatch` / `getWeeklyView` / `createWeeklyBatch`），SQL 在 `db/weeklyBatches.js`、`db/excerpts.js`、`db/openQuestions.js`、`db/artworkNotes.js`，AI 在 `ai/generateWeekly.js` + `prompts/weekly-batch.txt`，路由 `routes/weekly.js`。`verify-t8.js` 41/41（含 1 次真实 AI 生成）。详见 [specs/04](../specs/04-核心规则.md) 第十节

### T9 · 图片抓取与本地缓存（M5）

- **做什么**：从图片源取图 → **下载到本机** → 记 `local_path` → 通过 `/api/images/{filename}` 提供；实现 `POST /api/artworks/note` 与 `POST /api/open-questions/answer`。
- **产出物**：本地图片缓存目录 + 三个接口。
- **怎么算完成**：**断开外网刷新页面，画还能看到**；图片文件确实存在于本机磁盘。

### T13 · 碎片笔记本（M9 · v0.2，**先不排期**）

> 完整方案见 [02-技术方案.md](./02-技术方案.md) 第十二节。

**后端**

- **做什么**：`fragments` 表**已在 M0 建好**，这里只写逻辑。实现 `POST /api/fragments`（multipart：文件 + `kind` + 可选 `note`）——存进 M5 的本地图片目录 → 插一行 `status=pending` → **立刻返回**；**不等待地**调多模态模型，回写 `ai_summary` / `ai_tags` / `ocr_text` 与 `status`；实现 `GET /api/fragments`（`LIKE` 搜索，不上 FTS5）；**服务启动时扫一遍 `status=pending` 重跑**。
- **产出物**：两个接口 + 后台识别任务 + 启动补跑。

- **产出物**：碎片页。
