## 一、技术选型总表

| 零件 | 选型 | 说人话 | 对你的影响 |
| --- | --- | --- | --- |
| 页面（前端） | **React + Vite + TypeScript** | 搭乐高，零件现成 | 改样式 / 加功能便宜，不会被自己前期偷懒拖死 |

## 二、每个选择，展开说

### 1. 前端用 React

- **大白话**：做页面有两条路——**一块整木头雕**（纯 HTML，简单但改一处动全身）和**搭乐高**（React，零件现成）。你这个有 6 个页面 + 统计 + 错题队列，必须用乐高。
- **对你的影响**：**改的代价低**。设计稿改一版、想加一个"按画家串起来看"的页面，都不用推倒重来。
- **以后想改难不难**：**换框架很难**（等于重做），但**加东西很容易**。所以这个选择现在定了就别再动。

### 2. 后端用 Node.js

- **大白话**：一个在你电脑上默默跑的小程序，专门干三件事——**问 AI 要内容、把结果存下来、把数据算成统计**。
- **对你的影响**：你电脑上**只需要装一个 Node.js**。如果后端用另一种语言（比如 Python），你就得装两套环境，出问题也不知道该修哪套。
- **以后想改难不难**：**中等**。业务逻辑都在这一层，改动会比前端贵，但不像换语言那么伤。

### 3. 存储用 SQLite

- **大白话**：整个数据库就是**电脑上的一个文件**（像 `data.db`）。它比 Excel 结实的地方是：能秒查"所有关于'明清'的、我答错过的题"。
- **对你的影响**：**你的笔记不会丢在浏览器缓存里**——清缓存、换浏览器都不影响。想备份就是复制这个文件。
- **以后想改难不难**：**容易**。真要换也只需改后端一处，前端无感。

> **为什么不选 "数据存浏览器里"（纯网页方案）**：那样清一次缓存，你写的所有笔记和打卡记录**会全部消失**，而且 AI 的钥匙会暴露在浏览器里。这是这个方案唯一的硬伤，所以直接排除。

### 4. AI 用智谱（国内直连）

- **已定**：服务商 **智谱（open.bigmodel.cn）**，主模型 **`GLM-5.3-Flash`**（详见第七节）。
- **大白话**：每天出题、写解析、摘书里的段落，都是**发个请求问 AI，它回一段文字**。
- **对你的影响**：
  - **要花钱**（按用量）。但**每天只在首次打开时生成一次、当天复用**，用量很小。
  - **要给一把钥匙**（API Key，相当于"进 AI 大门的门禁卡"）。这把钥匙只存在你本机，不进代码库。
- **以后想改难不难**：**很容易**。国内几家（DeepSeek / 通义 / 智谱等）接口格式基本一致，换一家只改一行配置。

### 5. 图片境内外都取

- **大白话**：从博物馆的"开放素材库"里拿高清图。**大都会（Met）本身就有大量中国藏品**，所以"境内外都取"实际靠几家海外开放库就能覆盖中外。
- **对你的影响**：免费。但**图片必须下载到你本机缓存**——否则哪天对方改链接，你的画库就是一堆裂图。
- **以后想改难不难**：**容易**。多接一家就是多加一个"取图器"，不影响其它部分。

## 四、系统怎么跑（架构）

### 两条"流水线"

```
[你] → 浏览器打开 localhost
        │
        ├─ 前端（页面）── 展示题目、接收你的作答
        │
        └─ 后端（本机小服务）
              ├─ 问 AI：出题 / 写解析 / 摘段落      （联网）
              ├─ 去图片库：取当日那张画             （联网）
              └─ 读写 SQLite：题目 / 记录 / 笔记    （本机）
```

### 一条完整链路：早上打开网站会发生什么

1. 前端问后端："今天该给我什么？"
2. 后端先查 SQLite：
   - **有没有昨天没做完的题？** → 有就先把剩下的补上（进度保留）
   - **有没有到期的错题？** → 按 1/3/7/15 天查出来插进队列
3. 不够 10 题的部分，后端**问 AI 生成新题**，生成后**立刻落库**（当天再打开就不重复生成，也不重复花钱）
4. 前端拿到 10 题，渲染成页面
5. 你逐题作答 → 每题结果写回 SQLite → 后端更新错题的间隔和连对计数
6. 做完 10 题 → 写一条打卡记录 → 前端显示"今日已完成"

### 两个"进程"

- **后端**必须一直开着（它就是那个"后厨"）。启动方式是双击一个脚本，浏览器自动打开。
- **前端**平时由后端一起提供，你不用单独开。
- **启动方式分两步走**（2026-10-08 定）：**开发期先手动启动**（`npm run dev`），把主链路跑通；等推送落地（M8）时，再按第十一节改成**开机自启 + 托盘常驻**——因为要弹通知就必须有东西一直活着。

### 打开时要等多久

第 3 步"问 AI 生成新题"是**整条链路里唯一慢的一步**（补昨日剩余、查到期错题都是本地查表，毫秒级）。

- **采用同步阻塞**（2026-10-08 定）：前端发一次请求，等后端把 10 题凑齐一次性返回，期间显示 loading。**接口契约不需要加 `generating` 之类的字段**，实现最简单。
- 代价是当天首次打开要等几秒到十几秒；当天再打开因为已落库，是**秒开**。
- **失败不许白屏**：AI 超时或报错时，页面必须给出明确提示 + 重试按钮（见第九节风险表）。

## 六、关键规则与算法

> 给开发用。这里的每一条都来自 PRD 里的已确认决策。

### 1. 每日 10 题的组装顺序

```
① 若有昨日未完成题 → 优先插入（进度保留，隔天接着做）
② 插入所有"到期"的复习题（下次出现日 <= 今天）
③ 若不足 10 题 → 问 AI 生成新题补足
④ 题型上限校验：论述 ≤ 1、名词解释 ≤ 2、图像辨识 ≤ 2，其余为客观题
⑤ 中外美术史混合出现，不按时间线排序
⑥ 全部落库，当天固定不变（重复打开不重新生成）
```

**去重**：新题生成后算一个"内容指纹"（题干 + 核心标签的组合哈希），和库内已有题比对，重复则丢弃重生成。

### 2. 遗忘曲线 + 出队规则（2026-10-08 改）

| 事件 | 结果 |
| --- | --- |
| 首次答错 | 入队，间隔 = 1 天，连对计数 = 0 |
| 复习答对 | 连对计数 +1；间隔推进 1 → 3 → 7 → 15 天 |
| 复习答错 | 连对计数归零；间隔退回 1 天 |
| **在 15 天节点答对（走完全程）** | **出队**，不再出现 |

> **2026-10-08 变更**：原规则是"连对 2 次出队"，后果是 **7 天和 15 天这两个节点白设**，实际退化成 1/3。老叶决定**改为走完全程才出队**——一道错题要依次经过 1 → 3 → 7 → 15 四个节点，**在 15 天节点答对才出队**（等价于**连对 4 次**）。代价是错题陪跑更久，换来长期记忆真的被保住。

### 3. 打卡与连续天数

- **不断清零**：跨天未打卡时，"当前连续"归零，但**"最长连续"和"总完成天数"永久保留**。
- 统计页三个数都要展示：当前连续 / 最长连续 / 总完成天数。

### 4. 标签体系（出题均衡的依据）

```
中外：中国美术史 / 外国美术史
时期：史前 · 商周 · 秦汉 · 魏晋南北朝 · 隋唐 · 宋 · 元 · 明 · 清 · 近现代
      文艺复兴 · 巴洛克 · 洛可可 · 新古典 · 浪漫主义 · 写实 · 印象 · 后印象 · 现代 · 当代
流派/门类：文人画 · 院体 · 青绿山水 · 印象派 · 立体主义 ……
对象：作者 / 作品 / 技法
```

**出题均衡**：按标签分布控制，避免连续几天都在同一个时期。

### 5. 统计指标

- 连续打卡天数（当前 / 最长）、总完成天数
- 正确率：总体 + 按题型
- **薄弱点**：正确率最低的标签（如"明清"或"印象派"），按标签聚合算正确率后取倒数前三

## 七、外部接口

### 1. AI（国内直连）

- **已选定（2026-10-08）**：服务商 **智谱（open.bigmodel.cn）**，主模型 **`GLM-5.3-Flash`**（Model Code：`glm-5.3-flash`）。它是**原生多模态**——图片、视频、文本都收，**出题与读图一个模型全包**，满足第十节那条"一家同时具备出题与读图能力"的硬约束。上下文 1M，最大输出 128K。
- **备用 / 降级档**（不单独用，仅当主力不可用时）：`GLM-4.7-Flash`（纯文本，免费）、`GLM-4.6V-Flash`（视觉，免费）。
- **用途**：出题、写解析、生成书籍摘录、生成开放问题、读碎片截图
- **难度基线**：提示词里必须写死"对标各大美院美术史考研真题"（见 [03-MVP-Spec.md](./03-MVP-Spec.md) 第 2 节"难度定位"），否则默认出通识题，对目标用户太浅
- **形态**：OpenAI 兼容的 HTTP 接口（智谱提供该形态）
- **成本控制**：每天只生成一次并落库；当天复用；把思考压到最低档（见下）
- **约束**：Key 存本机 `.env`，**绝不写进代码或文档**

**两个容易踩的坑**

1. **思考 token 同样计费**。`glm-5.3-flash` **关不掉思考**（实测传 `thinking.type=disabled` 会被 1210 拒掉，只认 `enabled`），能做的是用 `reasoning_effort` 把它压到最低档。**实测同一提示词：默认档输出 29842 tokens（思考 25774）/ 266 秒，`low` 档输出 2785 tokens（思考 24）/ 71 秒——成本约 1/10。所以代码里固定写 `reasoning_effort: 'low'`。**
2. **图像辨识题的"作者 / 年代"不要指望 AI 认出来**，应**直接取博物馆元数据**（Met 接口里的 `artistDisplayName`、`objectDate`），AI 只负责写风格依据和干扰项——把幻觉风险最大的一环交给权威数据。

**选型结论**

模型已定为 **智谱 `GLM-5.3-Flash`**（2026-10-08 老叶拍板）。理由：它是唯一同时满足"能看图 + 一家管两件事 + 月成本 5 元以内"的选项；旗舰 `GLM-5.3` 虽更聪明但**只收文本、不能读图**，`GLM-4.7-Flash` 免费但**也不收图**。

看图能力**已于 2026-10-08 实跑验证通过**：传 `design/img/q-image.jpg`，`glm-5.3-flash` 正确说出作者、年代、藏馆与画面细节，无幻觉。实测记录见 [06-AI选型对比包.md](./06-AI选型对比包.md)。**注意：这个模型的思考关不掉，代码里统一用 `reasoning_effort: 'low'` 压到最低档（见上一节第 1 条）。**

### 2. 图片

| 来源 | 是否需密钥 | 特点 |
| --- | --- | --- |
| 大都会艺术博物馆（Met Open Access） | 否 | 起步最快，含大量中国藏品 |
| 芝加哥艺术博物馆 | 是（需申请） | 图质量高，西方现代收藏强 |
| 台北故宫开放资料 | 视接口而定 | 中文语境，中国书画强 |

- **必须本地缓存**：取到图后下载到本机，记 `local_path`，不使用外链直显。
- **Met 接口注意（2026-10-08 实测）**：旧搜索接口 `/public/collection/v1/search` **已于 2026-10-01 下线**，调用会返回一段提示 JSON（不是 `objectIDs`）。改用 `/public/collection/v1.1/search`（Elastic，带 `offset` / `limit` 分页）。取图：`/public/collection/v1/objects/{id}` 的 `primaryImageSmall`；图片站 `images.metmuseum.org` 可达，`en.wikipedia.org` 在国内网络不可达（不要用它当图源）。
- **设计稿已按此跑通**：`design/img/` 下 5 张公有领域真图（张瑞图《山水》、谢时臣《春山图》、董其昌《春山暖翠》、维米尔《持水壶的年轻女子》、张宇《松馆春云》）。

## 八、开发交接须知

> 给未来的开发 / AI 协作用。

### 环境与启动

- **运行环境**：Node.js（LTS 版本）
- **启动方式**：开发期手动 `npm run dev`（同时起前后端）；打包后一键脚本 → 起后端 → 自动打开浏览器 `localhost`。**开机自启留到 M8 推送时再做**。
- **数据文件位置**：项目内 `data/` 目录，含 SQLite 文件与图片缓存

### 工程结构（2026-10-08 定）

**一条规矩：竖着调，不许横穿。** `routes/` 只校验参数、不写业务；`services/` 是唯一规则之地；`ai/`、`images/`、`push/` 三个对外口子各只有一个入口文件能碰；`db/` 是唯一能碰 SQLite 的地方。

| 决定 | 选择 | 理由 |
| --- | --- | --- |
| 代码组织 | **npm workspaces 单仓两包**：`app/web/`（React+Vite+TS）+ `app/api/`（Node） | 一条命令同时起；接口类型可共用一份，改契约不易漏改两边 |
| 数据层 | **better-sqlite3 + 手写 SQL**（不上 ORM） | 同步接口、零配置、启动快；17 张表规模小，SQL 好读好调 |
| AI 调用 | **同步阻塞 + loading** | 契约不变，实现最简；当天二次打开因已落库是秒开 |
| 后端启动 | **开发期手动 → M8 再开机自启** | 先跑通主链路，不被环境问题分心 |

```
个人专注力/
├─ specs/            ← 实现规格（接口 / 数据模型 / AI 调用 / 核心规则）
├─ docs/             ← 决策文档（为什么这么做）
├─ app/
│   ├─ api/          ← 后端：Node
│   │   └─ src/
│   │       ├─ routes/      ← 只校验参数，不写业务
│   │       ├─ services/    ← 唯一规则之地（组题 / 判分 / 复习队列 / 打卡）
│   │       ├─ db/          ← 唯一能碰 SQLite 的地方
│   │       ├─ ai/          ← 唯一能碰智谱的地方
│   │       ├─ images/      ← 唯一能碰博物馆接口的地方
│   │       └─ push/        ← 唯一能碰桌面通知的地方（M8）
│   └─ web/          ← 前端：React + Vite + TS
├─ design/           ← 设计稿 + img/（本地缓存图）
└─ data/             ← 运行时数据：SQLite 文件 + 图片缓存（不进版本库）
```

### 编码硬约束

1. **AI 生成的内容必须落库**，不允许"只在内存里存在"——否则每次刷新都重复花钱。
2. **密钥只走 `.env`**，`.env` 加入忽略名单；文档、代码里不得出现 Key。
3. **图片一律本地缓存**，禁止外链直显。
4. **日期按本地时区（Asia/Shanghai）**，跨天判定以此为准。
5. **当天题目固定**：同一天重复打开不得重新生成。
6. **标记问题的题不再出现在每日题中**。

### 怎么算"做完了"

对照 [01-PRD.md](./01-PRD.md) 第 7 节的 10 条用户故事逐条验收：
- 每条故事的验收标准就是测试用例；
- 重点验证：当天不重复生成、错题按曲线重推、进度跨天保留、连续天数不清零。

## 九、技术风险

| 风险 | 会怎么表现 | 应对 |
| --- | --- | --- |
| **AI 内容出错** | 年代、作者归属错，你一眼看穿、失去信任 | 「标记问题」入口 + 已标记的题不再出现；错误累计 ≥ 5 道就必须改生成策略 |
| **外链图片失效** | 画库变成一堆裂图 | 图片一律下载到本机缓存 |
| **数据丢失** | 硬盘故障，全部记录消失 | 数据是单文件，定期复制 + 提供一键导出 |
| **生成慢 / 白屏** | 打开网站等很久或什么都不显示 | 每天首次生成后落库；生成失败要有明确提示与重试，不许白屏 |
| **重复题** | 每天刷到一样的题 | 内容指纹去重 |
| **AI 费用失控** | 反复生成、账单变高 | 当天只生成一次并复用；记录每日调用次数 |
| **换电脑要搬数据** | 没有云同步 | 明确接受：靠导出 / 复制 `data/` 目录搬家 |
| **密钥泄露** | Key 被写进代码或文档 | 只走 `.env`，交接时检查 |

## 十一、推送机制（MVP）

> 产品规则见 [03-MVP-Spec.md](./03-MVP-Spec.md) 第 3.4 节。**这一节只讲怎么实现。**

### 1. 架构上的一处改动：后端必须常驻

原来的设定是"双击脚本 → 起后端 → 打开浏览器"，用完就没了。**要弹通知，就得有东西一直活着。**

- 后端改为**开机自启 + 托盘常驻**（Windows：任务计划程序 / 启动文件夹）
- 浏览器可以关，后端不停
- 原"用时才起"的方式只保留为手动启动（调试用）

### 2. 每天的流程

```
到点（默认 21:00，可配）
   ↓
进程在跑吗？——没跑 → 跳过，不补发
   ↓ 在跑
今天的内容生成好了吗？——没有 → 先生成今日 10 题
   ↓
取当天的一个 hook（不剧透的引子）
   ↓
弹系统通知（可点击 → 今日页）
   ↓
写一条 push_log（防重复发）
```

### 3. 钩子（`hook`）从哪来

**不额外调 AI**：生成今日 10 题的提示词里，让模型**顺手输出一个字段 `hook`**——一句不剧透的引子。落在 `daily_sessions.hook`。

若当天已有 `hook`（如白天已生成过题），直接复用，不再生成。

### 4. 数据表

| 表 | 变化 |
| --- | --- |
| `daily_sessions` | **新增字段 `hook`**（当天通知用的一句引子，可空） |
| `push_log` | **新增表**：日期、发送时间、文案、是否送达——用于"同一天不重复发"与排查"今天怎么没弹" |

### 5. 硬防线（写进代码，不只是写进文档）

通知文案**永不出现**："你还没做""还差几题""连续要断了""进度 X/10"。

发送前做一次字符串检查，命中就改写成钩子型；**实在生成不出钩子，宁可不发，也不要发催办。**

### 6. 系统通知怎么弹

- Windows 用 `node-notifier`（SnackToast 后端），带**点击回调** → 打开浏览器到今日页
- 只做本机通知，**不接**飞书 / 邮件 / 微信（2026-10-08 决定）
- 已知坑：Windows「专注助手」会静音通知——所以**推送不是唯一入口**，主界面与书签照常可用

### 7. 配置项（写进 `settings`）

| 项 | 默认 |
| --- | --- |
| 开关 | 开 |
| 每天时间 | **21:00**（2026-10-08 定） |
| 时间窗 | 09:00–22:00（窗外不发） |
| 文案风格 | 钩子型（**不提供催办档位**） |

## 十二、v0.2 规划：碎片笔记本（内容入口）

> 不在 MVP 范围内（需求见 [01-PRD.md](./01-PRD.md) 第 8.1 节）。**但 `fragments` 表在 M0 建表时就一起建好**，避免 v0.2 再动数据结构。

### 1. 它解决什么

现在的内容都是"系统给的"（AI 生成 + 每周一批给一张画），缺了"我自己给"的那一路。碎片笔记本就是一个上传窗口：截图丢进来 → AI 读图出摘要与标签 → 存进碎片池。

**定位是起点不是终点**：碎片是原料，出口是被挑进"每周一批"、以及作为出题素材。

### 2. 数据表 `fragments`

| 字段 | 说明 |
| --- | --- |
| `id` / `created_at` | |
| `kind` | `artwork` / `text` —— 上传时手选的 |
| `image_path` | 本地文件名，走现有 `/api/images/` |
| `user_note` | 你手写的一句话，可空 |
| `ai_summary` / `ai_tags` | AI 读图产物，识别前为空 |
| `ocr_text` | `kind=text` 时抽出的文字 |
| `status` | `pending` / `done` / `failed` |
| `used_in_batch_id` | 用在哪个周批次，可空 |
| `used_in_question_id` | 用在哪道题，可空 |

后两个字段是"出口"留下的痕迹，**现在就要留**——否则以后无法回溯某张碎片去了哪里。

### 3. 接口

| # | 方法 | 路径 | 请求 | 响应 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 12 | POST | `/api/fragments` | multipart：`file`、`kind`（artwork/text）、`note?` | `{id, status:"pending"}` | **立刻返回**，不等 AI |
| 13 | GET | `/api/fragments` | `?q=` 搜索（可选） | `fragments[]` | 供碎片页列表 |

**不提供删除接口**：碎片不删，按时间沉底。

### 4. 上传链路（"秒回"怎么实现）

1. 前端：粘贴（`paste`）/ 拖拽（`drop`）/ 点选，配两个按钮选 `kind`
2. `POST /api/fragments` → 文件落到 `data/` 的图片目录（**复用 M5 的本地图片缓存链路，不新开存储**）
3. 插一行 `fragments`，`status = pending`，立即返回
4. **不等** AI：后台跑完再回写 `ai_summary` / `ai_tags` / `ocr_text`，置 `status = done`（失败置 `failed`）
5. **服务启动时扫一遍 `status = pending` 重跑** —— 否则进程重启会让碎片永远卡在"识别中"
6. 前端列表里该条先显示"识别中…"

### 5. 两类识别（`kind` 由上传时手选，不交给 AI 判断）

| `kind` | 做什么 |
| --- | --- |
| `artwork` | 多模态：画面描述——作者 / 年代 / 题材 / 可辨识特征，输出 JSON（summary + tags） |
| `text` | 多模态 OCR：抽出图里的文字，再顺带出 summary + tags |

拼提示词时把思考压到最低档（`reasoning_effort: 'low'`，同第七节第 1 条）。

### 6. 怎么进"每周一批"

生成周批次时，查 `kind = artwork AND status = done AND used_in_batch_id IS NULL`，取最近几条把摘要喂给 AI 挑选，选中后写 `used_in_batch_id`。

**兜底（必须实现）**：池子为空 / 全是 `pending` / 挑选失败 → **照常走"从博物馆库选"**。碎片永远不能卡住每周一批——这是"可选消费、不是待办清单"的技术落点。

### 7. 两个"不要做"

- **搜索不上 FTS5**：个人用一年也就几百条，`LIKE` 查 `ai_summary` / `ocr_text` / `user_note` 足够。
- **不新开存储**：与博物馆缓存图共用目录、共用 `/api/images/`，靠 `fragments` 表区分来源即可。

### 8. 手机入口（三条具体注意）

- 本机服务默认只允许本机访问：开发时 Vite 配 `server.host`，生产时后端监听 `0.0.0.0`，手机才连得上
- 前端与后端**同源**（后端 serve 静态文件）→ 不需要处理 CORS
- Windows 防火墙要放行端口；上传限 10MB，前端先压一遍（截图常有几 MB，多模态按图大小算钱与耗时）
- iPhone 截图是 PNG 没问题；相册照片可能是 HEIC，需限制或转码
