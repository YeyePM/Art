## 一之二、`POST /api/answers` 的字段与流程（2026-10-08 · T5 定稿）

**请求**

```json
{ "question_id": 12, "user_answer": "B", "self_grade": true }
```

- `question_id`：整数，必填。
- `user_answer`：**四种题型都必填**——先交上自己的作答，才换得到判定与参考答案。
- `self_grade`：**只用于"改判"**，取 `true` / `false`（`1` / `0` / `"correct"` / `"wrong"` 也接受）。只对名词解释 / 论述题有效，**客观题 / 图像辨识题带了它返回 `400`**（那两类由系统直接判，不给改）。

**判定流程**

| 题型 | 谁判 | 一次提交的结果 |
| --- | --- | --- |
| 客观题 / 图像辨识题 | **系统直接比** | 拿 `user_answer` 跟库里的答案比，立刻出 `correct` |
| 名词解释 / 论述题 | **AI 判** | 同步调一次 AI（十几秒），出 `correct` + `ai_comment` + `ai_errors` |

- 客观题答案是确定的选项字母，**不交给 AI**：直接比零延迟零成本，AI 反而更慢、还可能判飘。
- 名词解释 / 论述题不要求"跟参考答案一致"（论述题本来就没有标准答案）。AI 的判据是：立场是否明确、有没有具体作品或史实支撑、论证是否自洽；**事实性硬错误（作者 / 年代 / 流派 / 归属 / 地域搞错）一律判 false 并写进 `ai_errors`**。判分标准全文见 `app/api/prompts/grade-answer.txt`。
- **AI 判错是常态之一**，所以在 `correct` 之外还把它的理由和抓到的错误一起返回，用户可以据此**改判**（见下）。

**改判（"AI 判错了我再给它反馈"）**

拿到 AI 的判定后，用户不认时可以**再提交一次、带上 `self_grade`**，最终判定就听用户的：

```json
POST { "question_id": 12, "user_answer": "……", "self_grade": false }
→  { "correct": false, "ai_comment": "…AI 当时的点评…", "ai_errors": [...] }
```

- 改判**只覆盖 `answers.is_correct`**，并把 `is_self_graded` 置 1；AI 的原始判定留在 `answers.ai_correct` 里（以后能看"AI 判的跟你判的差多少"），点评与错误清单也不丢。
- 不需要新接口，复用这一个：**带 `self_grade` = 改判**。
- **AI 调不通时**（超时 / 内容审核拦截）返回 `correct: null` + `ai_failed: true`，**不落库**；前端提示用户自己定，用户带 `self_grade` 再提交一次即可（走的就是改判这条分支）。

**响应**

```json
{
  "correct": true,
  "explanation": "解析文字",
  "reference_answer": "B",
  "ai_comment": "AI 的点评（主观题才有，否则 null）",
  "ai_errors": ["事实性硬错误，每条一句"],
  "next_review_at": null
}
```

- `correct`：布尔；**`null` 表示没判上**（只有 AI 调不通时才出现），前端据此让用户自己定。
- `explanation`：题目解析（考点 + 最易错在哪）。
- `reference_answer`：客观题 / 图像辨识题是**正确选项的字母**（如 `"B"`）；名词解释 / 论述题是**参考答案原文**。
- `ai_comment` / `ai_errors`：AI 的点评与抓到的硬错误，**不落库以外的用途**——改判后仍会一起返回。AI 没参与则为 `null` / `[]`。
- `next_review_at`：这道题**下次什么时候再来**（`YYYY-MM-DD`），由 M3 的复习队列给出（`services/reviewQueue.js`）。答错 → 明天；复习答对 → 下一个节点（1→3→7→15）；**走完全程出队、以及本来就没进过队的题 → `null`**。前端拿它做"下次复习：X 月 X 日"一类提示，不参与对错判断。

**两条行为约定**

- 同一题同一天**重复提交是幂等的**（双击、断网重试）：**不重新调 AI、不再花钱**，直接返回首次的判定（含当时的点评），**也不会把复习间隔再往前推一格**。**带 `self_grade` 的那次不算重复提交，会覆盖判定**（复习队列也跟着按新判定重算一次）。
- 参数错误一律 `400`，响应体 `{"error": "中文说明"}`。

## 一之三、`GET /api/stats` 的字段（2026-10-08 · T7 定稿）

```json
{
  "current_streak": 3,
  "longest_streak": 7,
  "total_days": 20,
  "accuracy": {
    "overall": 0.78,
    "by_type": { "objective": 0.9, "term": 0.6, "image": 0.8, "essay": null }
  }
}
```

- `current_streak`：当前连续打卡天数。**最后一次打卡不在今天或昨天 → 归零**（今天还没过完，昨天仍算活着）；最长连续与总天数不受影响。
- `longest_streak` / `total_days`：历史最长连续、累计打卡天数，**永久保留**，断档不清零。
- `accuracy.overall`：总正确率，**0～1 的两位小数**；一次都没作答时是 `null`。
- `accuracy.by_type`：四种题型各一个正确率，**键一定齐全**；那一类没作答过就是 `null`（前端显示"—"而不是 0%）。
- 打卡**只由"完成当天题单"触发**（正常情况下就是 10 题；那天 AI 没补齐时，做完题单也算），与看画无关；**被耽误的那一天不补记打卡**。
- 无请求参数（不接受 `date` 之类，日期一律由后端按 Asia/Shanghai 算）。M7 已在这个接口上追加 `calendar[]`（打卡日历，见「一之六」），**字段只增不改**。

## 一之四、`GET /api/weekly` 的字段（2026-10-08 · T8/T9 定稿）

一个批次 = 1 张画 + 1 段书籍摘录 + 1 个开放问题，**管 7 天**（滚动 7 天，不是自然周）。

```json
{
  "batch_id": 3,
  "starts_on": "2026-10-08",
  "ends_on": "2026-10-14",
  "artwork": {
    "id": 7,
    "title": "持水壶的年轻女子",
    "artist": "约翰内斯·维米尔",
    "period": "1662",
    "school": null,
    "image_url": "/api/images/met-437881.jpg",
    "note": { "content": "留白很狠", "is_empty": false }
  },
  "excerpt": {
    "id": 2,
    "book_title": "历代名画记",
    "chapter": "卷一 论画六法",
    "source_text": "……原文……",
    "contact_line": "一句触点"
  },
  "open_question": {
    "id": 2,
    "stem": "完成感究竟从哪里来？",
    "reference_thoughts": "可从笔触与停笔的判断切入。",
    "user_answer": "我自己的回答……"
  }
}
```

- **滚动 7 天**：`ends_on = starts_on + 6 天`；未满 7 天时再打开**原样返回**（不调 AI、不联网）；满 7 天才生成新批次。新批次没生成出来（AI / 图源挂了）会退回当前批次，页面不空。
- `artwork.image_url`：**一律是本机缓存路径** `/api/images/<文件名>`，不返回任何外链；没缓存到图时为 `null`（画照留，界面显示无图）。图片文件名规则 `<来源库>-<外部 id>.jpg`（如 `met-437881.jpg`），文件在不在即"缓存命中没命中"。
- `artwork.note`：这件画"最新写的一句"；从没写过是 `null`；写过空内容是 `{content: null, is_empty: true}`（留空也算记了一笔）。
- `open_question.user_answer`：用户自己的回答；没写过是 `null`。
- `excerpt.source_text` 是**原文摘录**，`contact_line` 是把它接回当下的一句触点。
- 无请求参数（不接受 `date`）。`POST /api/artworks/note` 写画库（`{artwork_id, content}`，空内容也记、标 `is_empty`）；`POST /api/open-questions/answer` 写开放问题回答（`{open_question_id, content}`，留空不算答过）。参数错误一律 `400`。

## 一之五、`POST /api/flag` 与 AI 兜底（2026-10-08 · T10 定稿）

**标记（`POST /api/flag`）**

```json
{ "target_type": "question", "target_id": 12, "note": "答案看着不对" }
```

- `target_type` 只能是 `question` / `artwork` / `excerpt` / `open_question` / `fragment`，其余一律 `400`。
- `target_id` 必须是正整数，否则 `400`。
- `note` 可选，就是写给自己看的一句备注。
- 只记一笔流水到 `flagged_items`，**不校验对象是否真实存在**（本机自用，标错了也无害）。
- `target_type = "question"` 时，顺带把 `questions.is_flagged` 置 1 —— **出题池按它过滤**。之后这道题既不会从题库被选进来，**连"昨日未完成 / 到期复习"里的它也会被滤掉**（见 `services/questionPicker.js`）。
- 目前**没有"取消标记"接口**：要撤销就直接改库（`questions.is_flagged` 改回 0）。

**AI 兜底（体现在 `/api/today`）**

- `GET /api/today` 的响应多一个 `notice` 字段：**正常时为 `null`**，AI 没帮上忙时是一个对象 `{code, message}`。
  - `code` ∈ `no_key`（没配 Key）/ `timeout`（超时）/ `moderation`（内容审核拦了）/ `unavailable`（其它）。
  - `message` 是一句**人话**，前端直接显示即可，例："AI 服务暂时用不了。今天先看题库里现有的题，稍后重新打开这一页会自动重试。"
- **AI 挂了不返回 500、不白屏**：本次能给的题（昨日未完成 + 到期复习 + 题库现成）照常返回，`questions` 可能不足 10 道。
- **AI 挂了不落库**：这一次不写 `daily_sessions`（否则这天就被"固定"住、永远补不上）。所以**重新打开这一页就会自动重试**——这就是"可以重试"的落地方式。
- 超时与重试本身在 `ai/zhipuClient.js`（120 秒超时、最多 3 次、内容审核与 5xx 可重试、JSON 参数不被支持时自动去掉重试一次），M2/T3 起就有，M6 只是把失败**翻成人话并降级**。
- `POST /api/answers` 的 AI 失败是另一条既有约定（见「一之二」）：返回 `correct: null` + `ai_failed: true`、不落库，用户带 `self_grade` 自己定。

## 一之六、`GET /api/home` 与 `/api/stats` 的 `calendar[]`（2026-10-08 · T11 定稿）

**主界面概览（`GET /api/home`）**

```json
{
  "date": "2026-10-08",
  "today_progress": { "done": 6, "total": 10 },
  "stats": { "current_streak": 6, "accuracy": 0.78 },
  "weekly_summary": {
    "batch_id": 3,
    "starts_on": "2026-10-08",
    "ends_on": "2026-10-14",
    "artwork_title": "持水壶的年轻女子",
    "excerpt_book": "历代名画记",
    "has_open_question": true
  },
  "notice": null
}
```

- 三个板块各取一样东西，**只给粗略结论，不给正文**（主界面不泄露题目与解析）：
  - `today_progress`：今日进度，取值与 `GET /api/today` 的 `progress` **同源**（同一个 `getTodayView`），所以两处数字不可能对不上。
  - `stats`：只给 `current_streak`（当前连续）与 `accuracy`（总正确率，0～1 两位小数，无作答复 `null`），取值与 `GET /api/stats` **同源**。
  - `weekly_summary`：本周一批的摘要——画名 + 书名 + 有没有开放问题；**不含摘录原文、题干、参考答案**。没有批次时为 `null`。取值与 `GET /api/weekly` **同源**。
- `notice`：M6 的兜底照旧带出来（正常 `null`，AI 没帮上忙时 `{code,message}`，见「一之五」）。
- 无请求参数（不接受 `date`）。
- **副作用**：主界面是"当天内容就绪"的入口——第一次打开会按需把当天题单（与本周批次）备好，之后进今日页 / 本周一批秒开；幂等，一天只发生一次。
- **"数字完全一致"的落地方式**：不重算、只复用——三处分别直接调 `getTodayView` / `getStats` / `getWeeklyView`，谁都不新写一份口径。

**打卡日历（`GET /api/stats` 新增 `calendar[]`）**

```json
"calendar": [
  { "date": "2026-09-09", "checked_in": false },
  { "date": "2026-10-08", "checked_in": true }
]
```

- **最近 30 天（含今天），按日期升序，一天不缺**；只标"完成 / 未完成"（`checked_in`），不给时长、不给题量。
- 数据全部来自 `checkins` 表，**不新增数据表**；原 `current_streak` / `longest_streak` / `total_days` / `accuracy` 四个字段照旧。

## 一之七、`POST /api/push/test` 与推送机制（2026-10-08 · T12 定稿）

**手动触发一次推送**（验收用）

```json
// 请求：{ "at": "21:00" }   ← at 可省
// 响应：{ "ok": true, "sent": true, "reason": "sent", "date": "2026-10-08", "body": "…" }
```

- 带 `at`（`HH:MM`）：**走完整判断**（时间窗 09:00–22:00 + 到点 ≥ `at` 都生效），用来验证"窗外 / 未到点不发"；返回的 `reason` 就是没发的原因。
- 不带 `at`：**立即发**（跳过时间窗），但**仍守"同一天不重复发"**——今天已发过返回 `{sent:false, reason:"already_sent"}`。
- `at` 不是合法 `HH:MM` → `400`（中文提示）。
- `reason` 取值：`already_sent` / `before_window` / `after_window` / `before_time` / `no_hook` / `urging` / `sent` / `notify_failed`。

**每天定时自动推送**（`push/scheduler.js`，服务一启动就常驻）

到点（默认 21:00）按顺序过**四道关**，全过才弹一条 Windows 桌面通知（`node-notifier`，点它用默认浏览器打开今日页）：

| 关 | 判据 | 不过时 reason |
| --- | --- | --- |
| ① 今天没发过 | `push_log` 里没有今天的记录（一天一条） | `already_sent` |
| ② 在时间窗内且到点 | `09:00 ≤ 现在 ≤ 22:00` 且 `现在 ≥ 21:00` | `before_window` / `after_window` / `before_time` |
| ③ 当天内容已就绪、能取到 hook | 按需备好当天题单，取 `daily_sessions.hook` | `no_hook` |
| ④ hook 不含催办话 | 不含"你还没做 / 还差几题 / 连续要断了 / 进度 X/10" | `urging` |

- **hook 不额外调 AI**：它就是生成今日 10 题时顺手输出、由 T4 写进 `daily_sessions.hook` 的那一句；推送只取用。
- **通知标题 = `日拱一卒`**（`config.push.title`，改文案只动这一处）；正文就是当天的 hook。手动验收那条演示通知在此基础上加后缀 `（测试通知）`、正文固定为一句"这是测试通知"。
- **硬防线**：空钩子或被拦（`urging`）一律**不发**，**不改写成别的文案**——符合"生成不出钩子宁可不发"。
- **没开机就跳过、不补发**：无法持久化"当时在不在跑"，改用"服务启动先 tick 一次 + 时间窗判断"——开机在 21:30 会补上当晚这条，开机在 23:00（窗外）跳过。
- **同一天不重复发**：靠 `push_log.date` 的 UNIQUE 约束（`INSERT ... ON CONFLICT DO NOTHING`）。
- **通知失败降级**：弹通知抛错时不重试、仍记一条 `push_log`（`delivered:false`），避免反复重弹。
- **开机自启**：`npm run autostart` 把后端写进 Windows「启动」文件夹（建 `.lnk`）；**是后台常驻进程，不是托盘图标**。

## 二、`questions[]` 单项结构

```json
{
  "id": 12,
  "type": "objective",
  "stem": "题干文字",
  "options": ["A 选项", "B 选项", "C 选项", "D 选项"],
  "difficulty": "进阶",
  "image_url": "/api/images/xxx.jpg",
  "is_review": false,
  "tags": ["宋", "文人画"]
}
```

- `id` 是题库里的整数 id（对话时回传给 `POST /api/answers` 的 `question_id`）。原文示例里的 `"q_001"` 只是示意，**实际是整数**。
- `difficulty` 取 `基础 | 进阶 | 挑战`。
- `image_url`：图像辨识题是 `/api/images/<文件名>`（**本机缓存，不依赖外链**）；其余题型为 `null`。图片由 M5（`images/` 层）在生成题目或回填时下到本机，落 `questions.image_path`（由 `artworks.local_path` 派生）；**下载失败时仍为 `null`**，重跑 `09-M5-回填画作图片.bat` 即可补上。

`type` 取四个值之一：

| 值 | 含义 | options |
| --- | --- | --- |
| `objective` | 客观题 | 4 个 |
| `term` | 名词解释 | `null` |
| `image` | 图像辨识 | 4 个 |
| `essay` | 开放论述 | `null` |

## 三、一条必须守住的规则

**`/api/today` 绝不返回答案和解析。**

答案与解析只在 `POST /api/answers` 的响应里返回——包括主观题的参考答案，也必须等提交后才给。否则前端能提前拿到答案，判定环节就失效了。

---

## 四、前端 mock 约定

后端就绪前，前端用一份 `mock/today.json` 按上面的结构造 10 道题，要求：

- 四种题型都要有；
- 至少 1 道 `is_review: true`。

这样 UI 可以先跑通，不必等后端。

---

## 五、谁都不做（避免返工）

- 前端**不**直连 AI、**不**直接读数据库文件 → 一律走后端接口。
- 后端**不**关心页面长什么样、**不**写样式。
- 前端**不**自己算连续天数和遗忘曲线 → 这些逻辑只存在于后端一处。
