## 0. 一句话

组题层有一条"某题型题库里没有 → 退让成客观题把 10 道填满"的规则，副作用是 `needMore` 变成 0、**就再也不去生成图像辨识题了**。按口径 A，退让行为**保留**，但必须补一条"图像辨识题库存保鲜"，否则这个题型会永远消失。

## 1. 口径 A 到底定了什么（先读这段，别做反）

| | 含义 |
| --- | --- |
| **保留** | `questionPicker.js` 的退让：某题型没库存时，用没到上限的题（通常是客观题）填满当天 10 道。**当天题数优先**。 |
| **定位** | 题型构成从"固定配额"降级为"**尽力而为**"——凑不上不算 bug，但也不许把 10 道变成 8 道。 |
| **必须补** | **图像辨识题不能因此枯竭**：它不是"凑数选项"，是核心题型。库存不足时要**单独补货**（见 T14-B）。 |

## 2. 三条任务

三条都归到 **T14 · 修补：图像辨识题库存保鲜与坏题防线**，建议配一个 `verify-t14.js` 与 `测试\api\14-M1-验收图像题保鲜.bat`。

### T14-A · 库存保鲜（口径 A 的核心）

- **现在为什么不做**：`services/todaySession.js` 的 `buildTodaySession` 只在 `plan.needMore > 0` 时调 `generateAndStoreDailyQuestions`；而退让把 `needMore` 压成 0，于是**当天一次 AI 都不会调**，题库里的图像辨识题只减不增。
- **要做什么**：在 `buildTodaySession` 里，**除 `plan.needMore` 之外**再算一个"图像题库存缺口"，缺口 > 0 就**额外**调一次生成，**只往题库补货，不改当天题单**：
  - 缺口 = `config.typeLimits.image` − 库中"可用图像辨识题"数；小于 0 取 0。
  - "可用" = `type='image' AND is_flagged=0 AND options IS NOT NULL`（最后一条见 T14-B）。需要新增一个读函数（如 `db/questions.js` 的 `countUsableImageQuestions()`）。
  - 生成调用形如 `generateAndStoreDailyQuestions({ date, needMore: 缺口, needMoreByType: { image: 缺口 }, artworks })`；artworks 复用现有的 `resolveArtworks` / `images/artworkSource.js`。
- **为什么"只补货、不改当天题单"**：口径 A 要的是"当天不退让、不中途换题"。今天题单已经固定，补的货**明天自然被组题层用上**（图像题进候选池 → 构成就凑得上）。这也避免用户正做着题、题目被换掉。
- **落文档（别漏）**：`specs/04-核心规则.md` 第一节把"当日题型构成固定为论述 1 + 名词 2 + 图像辨识 2 + 客观 5"改写成"**尽力而为**：先保当天题数满 10；题型构成能凑就凑，凑不上时按'库存保鲜'单独补图像题"；并在 [questionPicker.js](../app/api/src/services/questionPicker.js) 退让那段（第 134–141 行）的注释里写明**退让是有意为之，别当成 bug 修掉**。

### T14-B · 坏图像题防线（防复发）

- **现象**：库里 id 486–489 四道早期生成的图像辨识题 `artwork_id` / `image_path` / `options` 全是 null。它们照样被 `getCandidates` 选进当天题单 → 界面没图，且 `services/grading.js` 的 `compareChoice` 两边都归一成 `null` → **怎么选都判"答错"**。
- **要做什么**：在 `db/questions.js` 的 `getCandidates` 上加一条过滤——**图像辨识题必须有 `options`**（`type != 'image' OR options IS NOT NULL`），坏题不进候选池。
- **已有数据的处置**：这 4 道**已由前端代删**（2026-10-08，见交接记录）。这条只是**防复发**，不用再清一次。
- **顺带一句口径**：图像辨识题的作者 / 年代一律取博物馆元数据、AI 只写风格依据与干扰项——这是老规则（`specs/03` 第四节），别为了"让坏题能用"去给 `options` 补默认值。

### T14-C · `progress.total` 与实际题数一致

- **现象**：`daily_sessions.question_ids` 会引用**已删除的题**（自测脚本 t2/t3/t4 会清空重灌题库），`getForDisplay` 拿不到这些 id 就跳过了，于是 `/api/today` 返回 9 道题、但 `progress.total` 还是 10 → 今日页显示"今日 9 题 / 进度 x/10"。（2026-10-08 实测：题单里挂着已不存在的 id 513。）
- **要做什么**：让 `progress.total` 等于**实际取到的题数**（`getTodayView` 里用 `questions.length`），或让 `buildTodaySession` 在保存前校验并剔除不存在的 id。**取前者更小改动**。
- **注意**：`progress.done` 的口径不变（当天已作答数），别顺手改。

## 3. 怎么算完成

1. 造一个"题库里没有任何可用图像辨识题"的场景（建议虚拟日 + 注入 artworks，别真调 AI 花钱），打开 `/api/today`：
   - 当天**仍然是 10 道题**（构成可能歪，这是口径 A 允许的）；
   - 但**题库里会被补出 2 道带 `options` 的图像辨识题**；把当天题单清掉重取，能取到图像题。
2. 手工插一道 `type='image' AND options IS NULL` 的假题，确认它**不出现在 `/api/today`**。
3. 把当天题单里塞一个不存在的 id，确认 `/api/today` 的 `progress.total` 与 `questions.length` **相等**。
4. `verify-t14.js` 全绿（尽量不花钱、不联网；确需真生成时控制在 1 分钱内），并按现有习惯补一个双击 bat。
